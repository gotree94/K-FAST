# 모듈 4. 모니터링 및 성능지표 이해

> **파일 경로** : `01_교육내용_준비자료/04_모니터링_및_성능지표_이해.md`
> **성격** : 실습 + 분석. LLM 서빙/추론의 성능 지표를 정의하고, furiosa-smi·furiosa-perf 등으로 측정·해석하는 모듈.
> **예상 시수** : 이론 1.5시간 + 실습 2.5시간

## 1. 학습 목표

1. 지연시간(Latency)·처리량(Throughput)·활용률(Utilization)의 개념을 정확히 설명한다.
2. LLM 서빙 지표(TTFT, TPOT, ITL, tokens/s, QPS, 백분위 지연)를 정의하고 계산·해석한다.
3. furiosa-smi로 NPU 전력·온도·코어 활용률·토폴로지를 확인한다.
4. furiosa-perf/furiosa-bench로 벤치마크를 수행하고 결과(CSV/보고서)를 해석한다.
5. 병목(컴퓨트/메모리/IO)을 판별하고 활용률 데이터로 최적화 방향을 제안한다.

## 2. 핵심 성능 지표 정의

### 2.1 일반 지표

| 지표 | 정의 | 단위 |
|------|------|------|
| Latency(지연시간) | 요청→응답까지 단일 추론 시간 | ms, us |
| Throughput(처리량) | 단위 시간당 처리하는 요청/토큰 수 | QPS, tokens/s |
| NPU Utilization | NPU가 실제로 연산에 쓰인 시간 비율 | % |
| TPS/Watt | 전력 1W당 처리 토큰 수 → 에너지 효율 | tokens/s/W |
| 백분위 지연(p50/p95/p99) | 전체 요청 중 해당 백분위 이하의 지연시간 → "꼬리 지연" 확인 | ms |

### 2.2 LLM 서빙 지표

| 지표 | 정의 | 의미 |
|------|------|------|
| TTFT (Time To First Token) | 요청 후 **첫 토큰**이 나올 때까지 시간 | 사용자 체감 응답성. Prefill 성능에 영향 |
| TPOT (Time Per Output Token) | 출력 토큰 **1개당** 생성 시간 | 생성 속도 체감. Decode 성능에 영향 |
| ITL (Inter-Token Latency) | 토큰 사이 간격(TPOT와 유사) | 생성 일관성 |
| Throughput (tokens/s) | 초당 생성 토큰 수 | 서버 효율. 동시성↑→활용률↑→처리량↑ |
| QPS (Queries Per Second) | 초당 처리 요청 수 | 서비스 용량 |
| p99 지연 | 99% 요청이 만족하는 지연시간 | "꼬리 사용자" 경험 품질 |

> **교수 포인트** : TTFT와 TPOT를 구분해야 한다. 사용자는 "첫 반응(어색한 지연 없이)"과 "연속 생성 속도"를 다르게 느낀다.

### 2.3 지표 간 트레이드오프 (핵심)

- 동시성(Concurrency)을 올리면 **처리량(tokens/s)은 증가**하지만, **개별 지연시간(TPOT/p99)은 증가**한다.
- 낮은 지연(좋은 UX) ↔ 높은 처리량(좋은 서버 효율) 사이의 균형을 목표(SLO)로 잡는다.
- 예: "p99 TTFT < 2초, p99 TPOT < 50ms" 같은 서비스 목표를 먼저 정의하고 운영.
- NPU 활용률이 낮은데 지연이 크면 → 병목이 NPU가 아니라 호스트/IO/스케줄링에 있을 가능성.

## 3. 모니터링 도구 실습

### 3.1 furiosa-smi (시스템 관리 인터페이스)

```bash
furiosa-smi info          # 전력(power), 온도(temp), PCI 링크 정보
furiosa-smi status        # NPU 상태 + 코어(PE)별 활용률
furiosa-smi topo          # NPU 토폴로지/NUMA
furiosa-smi ps            # NPU 점유 프로세스
furiosa-smi governor      # 전력 관리 프로파일(관리자 권한)
```

- `status` 예시(핵심 해석 포인트):
  ```
  +------+--------+----------------+------------------+
  | Arch | Device | Cores          | Core Utilization |
  +------+--------+----------------+------------------+
  | rngd | npu0   | 0 (occupied)~7 | Core 0: 99.47%,  |
  |      |        |                | Core 7: 99.45%   |
  +------+--------+----------------+------------------+
  ```
  - 코어(PE) 8개가 모두 occupied + 활용률 ~99% → NPU가 최대 활용 중.
  - 활용률이 낮으면 → 워크로드(배치·동시성) 부족 또는 병목이 다른 곳에 있음을 의미.

### 3.2 furiosa-bench (일반 모델 벤치마크)

```bash
# 지연 중심(L) 벤치마크: 1000쿼리, 워커 8, IO쓰레드 2
furiosa-bench model.onnx --workload L -n 1000 -w 8 -t 2

# 처리량 중심(T) 벤치마크
furiosa-bench model.onnx --workload T -n 10000 --batch 8 --workers 8
```

- 출력 항목 : QPS, 평균/최소/최대 지연, **p50/p95/p99 백분위**.
- `--output result.json`로 JSON 저장, `--trace-output`로 프로파일 추적.

### 3.3 furiosa-perf (LLM 서빙 벤치마크 자동화)

- 서버 기동 → vLLM 벤치마크 시나리오 실행 → **하드웨어 지표(전력·온도·활용률·호스트 CPU/메모리) 수집** → CSV/Markdown 요약 생성.

```bash
furiosa-perf run \
  --backend furiosa-llm \
  --hardware-type npu \
  --server-config examples/server/exaone4.yaml \
  --benchmark-config examples/bench/llm_scenario.yaml \
  --model-id furiosa-ai/EXAONE-4.0-32B-FP8
```

- 시나리오 : 입력 길이(ISL)/출력 길이(OSL)/동시성(CONC) 조합을 YAML로 정의.
- 산출물 : `summary_<ISL>_<OSL>.md/csv`, 시나리오별 `monitoring_log.csv`(전력·온도·활용률 시계열), 보고서 HTML.
- 활용 : RNGD와 GPU 비교 보고서(RTPS Pro 6000 대비 TPS/User, TPS/Watt, TTFT, TPOT) 생성 가능.

### 3.4 메트릭 노출 (Prometheus 연동)

- `furiosa-npu-metrics-exporter` : OpenMetrics 형식으로 NPU 지표(활용률·클럭·전력 등)를 HTTP로 노출.
- Prometheus 수집 + Grafana 대시보드로 운영 모니터링 구성 가능.

## 4. 성능 데이터 해석 (분석 가이드)

### 4.1 해석 순서

1. **목표 설정 확인** : 이 배포의 목표가 지연인지 처리량인지(SLO) 정의.
2. **지표 측정** : TTFT, TPOT, tokens/s, p50/p95/p99, NPU 활용률, 전력.
3. **병목 판별** :
   - NPU 활용률 높고(>90%) 지연도 크면 → NPU 컴퓨트 용량 부족 → 카드 추가/양자화.
   - NPU 활용률 낮고 지연 큼 → 호스트/IO/컴파일/스케줄링 병목 → 워커·배치·동시성 조정.
   - 전력·온도가 한계 도달 → 서멀/전원 제약 확인.
4. **최적화 방향 도출** :
   - 배치/동시성 증가 → 처리량↑ (지연과 균형).
   - INT8/FP8 양자화 → 메모리 감소·속도↑.
   - `max_model_len`(KV 캐시 예약) 조정 → 메모리 효율.
   - 병렬 분산(텐서/데이터 병렬) → 모델 규모·처리량 확장.

### 4.2 사례 해석 연습

**사례 1** : `furiosa-smi status`에서 npu0 코어 활용률 40%, p99 TTFT 5초.
→ 해석 : NPU가 놀고 있음. 병목이 NPU가 아님 → 요청 패턴/워커 수/호스트 스레드/IO 파이프라인 점검, 동시성 부족 여부 확인.

**사례 2** : 동시성 1→64로 올렸더니 tokens/s 100→800으로 증가, TPOT 20ms→80ms로 증가.
→ 해석 : 정상적 트레이드오프. 서비스 SLO(예: TPOT 100ms 이하)를 지키는 선에서 동시성을 유지하는 게 적절.

**사례 3** : 70B 모델 1카드에서 OOM 발생.
→ 해석 : 가중치+KV 캐시가 48GB 초과 → 2~4카드 텐서 병렬 또는 INT8/FP8 양자화 모델 사용.

## 5. 실습 설계 (예시)

| 순서 | 실습 | 목적 |
|------|------|------|
| 1 | `furiosa-smi status`로 유휴/부하 상태 읽기 | 상태 읽기 |

## 6. 핵심 포인트 요약

- 지연(개별 사용자)과 처리량(서버 효율)은 **상충**하며, SLO로 균형을 관리한다.
- LLM 지표는 TTFT(첫 토큰)/TPOT(이후 토큰)을 구분해야 한다.
- NPU 활용률은 "최적화 여부의 신호"이지 성능 그 자체가 아니다. 낮으면 병목을 찾아라.
- 모니터링은 furiosa-smi(실시간)·furiosa-perf(벤치마크)·metrics-exporter(운영)로 구분.
- 전력/온도도 중요한 운영 지표 — TDP(150W 수준) 초과 여부를 점검.

## 7. 예상 Q&A

- **Q. 토큰/s만 보면 되지 않나요?** → A. 처리량만 보면 개별 사용자 체감(지연)을 놓칩니다. TTFT·TPOT·p99와 함께 봐야 합니다.
- **Q. NPU 활용률이 100%면 성능이 좋은 건가요?** → A. 최적화가 잘 되었다는 신호이지만, 동시에 용량이 꽉 찼다는 뜻이므로 추가 요청 증가 시 지연이 급증할 수 있습니다. 활용률·지연·처리량을 함께 봐야 합니다.
- **Q. 지연이 큰데 활용률은 낮아요. 어떻게 해야 하나요?** → A. NPU 외부(호스트 IO, 전처리, 스케줄링, 워커 수) 병목을 먼저 의심하고, 벤치마크/프로파일로 구간별 시간을 측정합니다.
- **Q. furiosa-perf와 furiosa-bench 중 뭘 써야 하나요?** → A. ONNX/TFLite 등 일반 모델은 furiosa-bench, LLM 서빙 성능(생성형)은 furiosa-perf가 적합합니다.
